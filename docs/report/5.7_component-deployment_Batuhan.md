### 5.7.x UML Component Diagram

Diagram: `docs/diagrams/5.7_component-diagram_Batuhan.puml` (PNG: `5.7_component-diagram_Batuhan.png`).

The system has two deployable components that talk only through one interface, the REST API. Inside each, the sub-components follow the layers of 5.8.1. To keep the diagram readable, the six services are drawn inside one "Application services" component, and one arrow stands for "every service uses Repositories"; the table below gives the dependencies of each service.

| Component | Part of | Responsibility | Provides | Requires |
|---|---|---|---|---|
| Pages | Web Client | The 12 screens (search, reservation, my reservations, check-in, notifications, admin screens). | — | AuthModule, QrScanner, ApiClient |
| AuthModule | Web Client | Keeps the JWT in `sessionStorage`, knows the current user, guards pages by role. | Current user, login, logout | ApiClient |
| QrScanner | Web Client | Reads the door QR code with the phone camera; fallback field for the 6-digit code. | Scanned code | Browser camera |
| ApiClient | Web Client | One typed function per endpoint E01–E23; adds the token; turns errors into `ApiError`. | Typed API calls | REST API |
| HttpLayer | CampusSlot API | Routes, controllers and middleware (auth, role, validation, rate limit, error handler). | **REST API /api/v1** | The services |
| AuthService | CampusSlot API | Register, log in, issue JWT, current user. | UC-01 | Repositories |
| ResourceService | CampusSlot API | Search, availability, create and edit resources, generate door codes. | UC-02, UC-07 | Repositories |
| ReservationService | CampusSlot API | Create (rules R1–R5), cancel (R6), list, approve and reject (R5). | UC-03, UC-04, UC-06, UC-10 | Domain, Repositories, NotificationService |
| CheckInService | CampusSlot API | QR or code check-in inside the R7 window. | UC-05 | Domain, Repositories, NotificationService |
| NotificationService | CampusSlot API | Writes and lists in-app notifications. | F4 | Repositories |
| ReportService | CampusSlot API | Occupancy, no-show report, penalties. | UC-08 | Repositories |
| Domain | CampusSlot API | Rule validators R1–R4, ReservationStateMachine, time windows R6–R9. | Rule checks, allowed transitions | — |
| Repositories | CampusSlot API | Data access for the six tables through Prisma Client. | Data access | SQL interface |
| SystemScheduler | CampusSlot API | Runs J1–J4 every 60 seconds. | UC-09 | ReservationService, NotificationService |
| PostgreSQL | External | Stores the six tables and enforces unique and exclusion constraints. | SQL interface | — |

**Why this split.** The web client and the API share no code at run time, only the REST contract in 5.8.4. That lets Enes and Erol work in parallel from the same contract (5.5, activities L–N and I–K). The scheduler is a component of the API, not a separate service, because it must use the same rules and the same transaction as the HTTP side.

### 5.7.x UML Deployment Diagram

Diagram: `docs/diagrams/5.7_deployment-diagram_Batuhan.puml` (PNG: `5.7_deployment-diagram_Batuhan.png`).

The diagram shows the pilot and demo setup, which is Scenario A in 5.11 (free tiers). Scenario B in 5.11 uses the same nodes on paid plans; only the plans change, not the diagram.

| Node | Type | Deployed artifact | Communication |
|---|---|---|---|
| User device (phone or computer) | Device | — | — |
| Web browser | Execution environment on the user device | Running copy of the SPA | HTTPS to Vercel (load the app) and to Render (API calls) |
| Camera | Device | — | Used by the browser for the QR scan. Browsers allow camera access only in a secure context (HTTPS), so every node the browser talks to uses HTTPS (NFR-04). |
| Vercel | Static hosting / CDN | `frontend/dist` (built by `npm run build`) | HTTPS |
| Render web service | Server | `campusslot-backend` (Express API and SystemScheduler in one Node.js process) | HTTPS from the browser; PostgreSQL protocol over TLS to Neon |
| Node.js ≥ 20.19 | Execution environment on Render | Same as above | — |
| Neon | Database server | PostgreSQL database `campusslot` (tables from the Prisma migrations) | PostgreSQL protocol over TLS |
| GitHub | Source repository | Repository `MertTomak/SWE307-Term` | Vercel and Render build and deploy from `main` |

**Configuration.** The backend reads `DATABASE_URL`, `JWT_SECRET`, `CORS_ORIGIN` (the Vercel URL, so only our frontend may call the API) and `PORT` from the hosting platform's environment settings. The frontend reads `VITE_API_URL` at build time. No secret is in the repository.

**Risk: the scheduler and a sleeping server.** The Render free web service spins down after 15 minutes without inbound traffic (5.11). While it is asleep, the SystemScheduler does not run either, so no-shows and penalties are recorded late. The data stays correct, because the jobs catch up at the next start (5.8.4.9), but a user may see a stale status for a while. For the live demo the team either keeps the service awake before the demo or uses the paid instance of Scenario B for the presentation week. [TBD: team decision]

**Risk: first request after idle.** Neon Free scales to zero after 5 minutes idle (5.11), so the first query after a pause is slower. Before the demo, open the app once to wake both services.
