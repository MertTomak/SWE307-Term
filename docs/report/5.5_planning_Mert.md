## 5.5 Software Process Model and Project Management (planning part)

### 5.5.1 Process Model

We selected **Scrum** (Schwaber & Sutherland, 2020) with two one-week sprints followed by a final stabilisation and delivery week. Sprint 1 (18–24 Nov) covers analysis, design and the foundation features F1 and F2. Sprint 2 (25 Nov–1 Dec) covers F3–F8 and ends with the code freeze on 1 December. The last week (2–6 Dec) is reserved for system testing, report integration, the presentation and the video, and delivery. Only blocker defects are fixed in that week.

Scrum suits this project for four reasons:
- The deadline is fixed at 19 calendar days, and Scrum's time-boxed sprints fit that.
- A seven-person team learns the domain while working, so requirements will be refined. Short feedback cycles catch misunderstandings early.
- A working increment exists at the end of each sprint.
- F1–F8 form a prioritised backlog that can be split between sprints.

We did not select **Waterfall**, the sequential model described by Royce (1970/1987). It delivers a working system only at the end, so late defects or requirement changes cannot be absorbed in 19 days. It also leaves testing for the last phase. We did not select **Spiral** (Boehm, 1988). It is aimed at large, high-risk projects and needs formal risk analysis and prototyping in every cycle. That overhead is too high for a small project with a fixed scope and a known technology stack (React, Express, PostgreSQL).

**Scrum roles (proposed):** Mert = Scrum Master and Project Manager; Zeynep = Product Owner (backlog owner); other members form the Development Team. Ceremonies are adapted to the course: sprint planning at the start of each sprint, a short daily check-in, a sprint review and a retrospective at the end of each sprint.

### 5.5.2 Planning Assumptions

- **A1** Duration unit is the calendar day; the team works 7 days a week.
- **A2** TE values are rounded to 2 decimals and the rounded values are used in the schedule.
- **A3** Activity durations are independent and the path duration is approximately normal (standard PERT assumption).
- **A4** "Code freeze" means no new features after 1 Dec. Only blocker fixes are allowed.
- **A5** Project start is 18 Nov 00:00 (t = 0) and the deadline is 6 Dec 23:59 (t = 19).
- **A6** The tech stack is fixed, so architecture work can start right after kickoff.

Day numbering: Day 1 = 18 Nov, Day 14 = 1 Dec (code freeze), Day 17 = 4 Dec (report PDF), Day 19 = 6 Dec (deadline).

*(A1–A6 are numbered locally; they may need renumbering when merged into the global assumption list.)*

### Probability of finishing on time (PERT)

Path variance = sum of the Var values of the critical activities. Expressed in 36ths, A 1, B 1, C 4, G 4, L 4, M 4, P 1, Q2 1, W 4, Y 1 gives 25/36 = 0.6944.
σ = √0.6944 = 0.8333.

**Whole project:** Z = (19 − 18) / 0.8333 = 1.20, Φ(1.20) = 0.8849, so about **88.5%** on time.

**Code freeze:** the path A–B–C–G–L–M–P has variance 19/36 = 0.5278, σ = 0.7265. Z = (14 − 13.5) / 0.7265 = 0.69, Φ(0.69) ≈ 0.755, so about **75%** to freeze on time.

Caveat: the normal approximation ignores near-critical paths (K, J, Q1 have 0.33 slack). The real probability is somewhat lower than computed. The freeze probability is the main schedule risk.
