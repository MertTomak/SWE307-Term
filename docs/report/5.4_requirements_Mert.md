### 5.4.1 Actors and roles

| Actor | Role in the system | Role value | Note |
|---|---|---|---|
| Campus User | Abstract actor. Anything a Student or Academic Staff member can do. | — | Student and Academic Staff both derive from it. |
| Student | Searches resources, reserves, cancels, checks in. | `STUDENT` | Active reservation limit 2 (R2). |
| Academic Staff | Same as Student. | `ACADEMIC_STAFF` | Active reservation limit 5 (R2). |
| Resource Admin | Manages resources, approves equipment reservations, sees occupancy and no-show data. Does not reserve or check in (D3). | `RESOURCE_ADMIN` | Account created by seed data, not by self-registration (FPA assumption FP11, FR-02). [TBD: confirm] |
| System Scheduler | Time-triggered actor. Marks no-shows and applies penalties. | — | Not a person. |

Resource types: `ROOM`, `LAB`, `EQUIPMENT`. Reservation states: `PENDING_APPROVAL`, `CONFIRMED`, `CHECKED_IN`, `COMPLETED`, `CANCELLED`, `NO_SHOW`, `REJECTED`.

### 5.4.2 Business rules

These are fixed by the project card. The functional requirements below refer to them by ID.

| ID | Rule |
|---|---|
| R1 | A reservation lasts at most 3 hours. |
| R2 | Active reservation limit: Student 2, Academic Staff 5. |
| R3 | Reservations for the same resource cannot overlap in time. |
| R4 | A user with a running penalty cannot make a reservation. |
| R5 | `EQUIPMENT` reservations need admin approval (`PENDING_APPROVAL`). `ROOM` and `LAB` reservations go directly to `CONFIRMED`. |
| R6 | A reservation can be cancelled until its start time. |
| R7 | QR check-in window: from 10 minutes before the start to 15 minutes after the start. |
| R8 | If there is no check-in 15 minutes after the start, the reservation becomes `NO_SHOW` and the resource is released. |
| R9 | 3 `NO_SHOW` in the last 30 days give a 7-day reservation ban (Penalty). |

### 5.4.2a Open decisions with a PM-proposed default

The project card leaves these points open. The PM proposes the default below so that the requirements, the FPA count and the service layer can move on. **All four were proposed by Mert. The Business Analyst (Zeynep) confirmed all four unchanged on 26 Nov 2026; the backend confirmation by Erol is tracked in HANDOFFS (H10).** If a default changes, the FRs in the last column change with it.

| ID | Open point | Default (proposed by Mert; confirmed by Zeynep on 26 Nov 2026) | FRs affected |
|---|---|---|---|
| D1 | What counts as an "active" reservation in R2 | A reservation is active when its start time is in the future **and** its status is `PENDING_APPROVAL` or `CONFIRMED`. A reservation that has started (`CHECKED_IN`) or ended, and `CANCELLED`, `REJECTED`, `NO_SHOW` and `COMPLETED` reservations, do not count. | FR-15, FR-27, FR-48 |
| D2 | Whether `PENDING_APPROVAL` blocks the slot | Yes. A `PENDING_APPROVAL` reservation is included in the R3 overlap check, so nobody else can book the slot while the admin decides. When it becomes `REJECTED` or `CANCELLED`, the slot is free again. | FR-12, FR-16, FR-48, FR-55 |
| D3 | Whether a Resource Admin can reserve | No. `RESOURCE_ADMIN` only manages (resources, approvals, reports) and does not create reservations or check in. | FR-05, FR-13, FR-34 |
| D4 | An `EQUIPMENT` reservation that is not decided by its start time | The System Scheduler sets it to `REJECTED` at the start time and the user gets an in-app notification. | FR-55 |
