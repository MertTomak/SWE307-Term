## 5.12 Implementation and Testing: Test Plan (draft v1, 25 Nov 2026)

**Owner.** Görkem (QA/Test Engineer). The test results, the screenshots of the running application and the run instructions are added to 5.12 after the tests are run (1–3 Dec).

**Inputs.** Requirements FR-01 to FR-55 and NFR-01 to NFR-23 (5.4 v2), use cases UC-01 to UC-10 and decision tables DT-1 and DT-2 (5.6), the API contract and error codes (5.8.4), the security tests ST-01 to ST-15 (5.8.5.6) and the seed data in `backend/prisma/seed.ts`.

**Status of the columns.** "Actual result", "Pass/Fail" and "Evidence" are empty on purpose. They are filled in only from a real run of the tests; no result in this section is written in advance.

### 5.12.1 Test approach

| Level | What is tested | How | Who runs it |
|---|---|---|---|
| Automated API tests | Business rules R1–R9, the rule order of DT-1, the check-in window and the scheduler jobs, error codes, role checks. All boundary values that depend on the clock (exactly 10 and 15 minutes, exactly 3 hours, 30 days). | Vitest + Supertest against the Express app and a separate test database, in `/backend`. `npm test` skips the tests whose backend code does not exist yet; the test run for this report uses `npm run test:full`, which fails if the test database, `src/app.ts` or `src/jobs/index.ts` is missing, so a skipped test can never be counted as passed. The clock is set in the test (see TP-A2), so a boundary can be tested to the second. Marked **A** below. | Görkem; also on every pull request (GitHub Actions) if set up in time. |
| Manual system tests (end-to-end) | Complete user flows in the browser, from the screens to the database: register, search, reserve, cancel, QR check-in on a phone, admin approval, reports. | By hand on the deployed HTTPS URL and on a local copy, following the steps in the table. A screenshot is taken for each result. Marked **M** below. | Görkem; a second team member repeats the Must cases on another device. |
| Non-functional tests | Performance (NFR-11, NFR-12), compatibility and phone layout (NFR-17, NFR-18), server clock (NFR-10), keyboard use (NFR-20). | Load tool, timed check-in on phones, browser matrix. | Görkem |
| Security tests | ST-01 to ST-15 from 5.8.5.6 (authentication, authorisation, rate limits, data exposure, HTTPS, CORS, dependencies). | Automated where possible, otherwise manual (5.12.4). | Görkem |
| Regression | After every bug fix: the test case that found the bug, plus the full automated suite. | `npm test`; failed manual case repeated. | Görkem |

**Test design techniques.**
- **Decision table testing:** every reduced rule of DT-1 and DT-2 (5.6.5) has at least one test case.
- **Boundary value analysis:** for every limit, the value on the limit and the value just outside it (3 h / 3 h 01 min, start − 10 min / start − 10 min − 1 s, start + 15 min / start + 15 min + 1 s, 2nd / 3rd active reservation, 3rd no-show inside / outside 30 days, password 8 characters / 72 bytes).
- **Equivalence partitioning:** one representative per class where values behave the same (for example one `ROOM` and one `LAB` request are enough for "creates `CONFIRMED`").
- **Use case testing:** the main flow and the alternative flows of UC-01 to UC-10 (5.6.2).

### 5.12.6 Entry and exit criteria, defect handling

**Entry criteria** (before the test run on 1–3 December): the code freeze build is deployed; `npm run test:full` runs with no skipped test; the seed has been run with a secret `SEED_PASSWORD`.

**Exit criteria** (before the report is closed on 4 December):
- Every test case linked to a Must requirement has passed.
- No open defect with severity Blocker or Major.
- Every failed Should case and every open Minor defect is listed in 5.12 with its reason.

**Defect handling.** Every failure is opened as a GitHub Issue in the project repository, titled `[TC-xx] <short description>`, with the steps, the expected and the actual result, the screenshot and a severity:

| Severity | Meaning | Example |
|---|---|---|
| Blocker | A feature F1–F8 cannot be used or the demo stops. | Check-in always fails. |
| Major | A business rule gives a wrong result. | A 4-hour reservation is accepted (R1). |
| Minor | Wrong text, layout or a Should requirement. | The rejection reason is cut off on a phone. |

The issue is assigned to Erol (backend) or Enes (frontend). After the fix, the test case is run again (regression) and the issue is closed with the commit that fixed it. After the code freeze only Blocker defects are fixed (NFR-23).

### 5.12.8 Assumptions and open points

- **TP-A1.** The test cases use the error codes and the endpoints of the API contract (5.8.4, draft v1). If the contract changes, the expected results change with it.
- **TP-A2.** The automated tests set the clock with Vitest fake timers (only `Date` is faked). The backend therefore reads the time for R6–R9, the token lifetime and the scheduler from JavaScript (`new Date()`, `Date.now()`) or from a `now` parameter, not from the database (`now()` in SQL). Agreed contract in `backend/tests/README.md` (H33).
- **TP-A3.** `backend/src/jobs/index.ts` exports `runSchedulerOnce(now?: Date)`, one scheduler run with the jobs in the order J3, J1, J2, J4, so a test does not wait 60 seconds. `backend/src/app.ts` exports the Express app without calling `listen()` (H33).
- **TP-A4.** "Day +n" and the seed states in 5.12.2 are valid right after `npm run db:seed`. Manual tests that change data (TC-24, TC-41, TC-42, TC-45) are run after the read-only ones, or the seed is run again.
- **Open.** The load test tool for NFR-11: `autocannon` (an npm package, so no other runtime is needed) is proposed [TBD: confirm at the test run].
- **Open.** The expected occupancy rate in TC-46 needs the daily opening hours [TBD: H08].
- **Open.** TC-36 and TC-37 follow API-A7 (no-shows counted by start time). If the answer to H09 changes how earlier no-shows are counted, TC-37 changes.
