## 5.8 Technical Architecture (draft v1, 23 Nov 2026)

**Owner.** Cemal Batuhan Baş (System Architect). This file holds 5.8.1 Overall architecture and 5.8.2 Technology stack. 5.8.3 Data model is written by Erol. 5.8.4 API / interface design is in `5.8_api-design_Batuhan.md`. 5.8.5 Security and data privacy follows.

### 5.8.1 Overall architecture

CampusSlot is a **three-tier web application with a layered backend**: a single-page web client, one REST API server that also runs the System Scheduler, and one PostgreSQL database. The source code of both tiers is in one repository (`/frontend`, `/backend`).

Diagram: `docs/diagrams/5.8_architecture-diagram_Batuhan.puml` (PNG: `5.8_architecture-diagram_Batuhan.png`).

#### Layers

| Layer | Where in the code | Responsibility | May call |
|---|---|---|---|
| **Presentation** | `frontend/src` (React SPA) | Screens, navigation, role-based page guards, QR scanning with the camera, showing times in Europe/Istanbul. Holds no business rule; every rule is checked again on the server (NFR-03). | Application layer, only through the REST API (`frontend/src/api`). |
| **Application** | `backend/src/http`, `backend/src/services`, `backend/src/jobs` | HTTP routes and middleware (authentication, role check, input validation, rate limit, error handler), controllers that turn HTTP requests into service calls, and services that run one use case each inside a database transaction. The System Scheduler jobs J1–J4 also live here: they are a second entry point next to HTTP and call the same services. | Domain layer, Data layer. |
| **Domain** | `backend/src/domain` | The business rules R1–R9 in plain TypeScript: one validator class per reservation rule R1–R4 (Strategy pattern), the reservation state machine with the 7 statuses (State pattern), the time windows for R6, R7, R8 and R9. No Express, no Prisma, no clock of its own (the current time is passed in). | Nothing. |
| **Data** | `backend/src/repositories`, `backend/src/db`, `backend/prisma` | Repositories that read and write the six tables (Repository pattern), the single Prisma Client, migrations and database constraints. | PostgreSQL. |

**Dependency rule.** A layer may call only the layers below it. The Domain layer depends on nothing. Reason: R1–R9 are the part of the system that the report, the decision tables (5.6) and the tests (5.12) all refer to. Keeping them free of the web framework and the database lets Görkem test every rule with a plain unit test, without a server or a database (NFR-21).

#### Why a modular monolith and not microservices

All backend modules run in one Node.js process and share one database. The team has two developers and a code freeze on 1 Dec 2026 (5.5). Separate services would add network calls, separate deployments and distributed transactions, while the business rules need one transaction across Reservation, Penalty and Notification (for example J1 sets `NO_SHOW` and creates a `Penalty` together). The module boundaries (services, repositories) keep a later split possible. Alternatives are compared in 5.9.

#### Proposed backend folder structure

This is the target structure for Erol's code. Names may change while coding; the class diagram in 5.7 follows the final code.

```
backend/src/
  server.ts                  starts the HTTP server and the SystemScheduler
  app.ts                     Express app: middleware order, routes, error handler
  config/env.ts              reads and checks environment variables
  http/
    routes/                  one router per area: auth, resources, reservations, check-ins, notifications, admin
    controllers/             request → service call → DTO
    middleware/              requireAuth, requireRole, validate (zod), rateLimit, errorHandler
    schemas/                 zod schemas of request bodies and queries
    dto/                     mappers from database records to the DTOs in 5.8.4.5
  services/                  AuthService, ResourceService, ReservationService, CheckInService,
                             NotificationService, ReportService
  domain/
    rules/                   ReservationRule (interface), DurationRule (R1), ActivePenaltyRule (R4),
                             ActiveLimitRule (R2), OverlapRule (R3)
    state/                   ReservationStateMachine (allowed transitions of the 7 statuses)
    time.ts                  R6 cancel deadline, R7 check-in window, R8 no-show limit, R9 30-day window
    errors.ts                DomainError (code, rule, details) → mapped to the error format in 5.8.4.3
  repositories/              UserRepository, ResourceRepository, ReservationRepository,
                             CheckInRepository, PenaltyRepository, NotificationRepository
  jobs/                      SystemScheduler, NoShowJob (J1), CompleteJob (J2), AutoRejectJob (J3), ReminderJob (J4)
  db/prisma.ts               single PrismaClient (already on main)
```

#### How one request flows through the layers (UC-03 Make Reservation)

1. The New Reservation page calls `api.reservations.create(...)`; the API client sends `POST /api/v1/reservations` with the JWT.
2. Middleware: `requireAuth` checks the token, `requireRole('STUDENT','ACADEMIC_STAFF')` checks the role, `validate` checks the body with zod.
3. `ReservationController` calls `ReservationService.create(userId, input, now)`.
4. `ReservationService` loads the resource, then runs the rule validators in the order of 5.8.4.7 (R1 → R4 → R2 → R3). The first failing rule throws a `DomainError` with its code.
5. `ReservationStateMachine` gives the first status: `PENDING_APPROVAL` for `EQUIPMENT`, `CONFIRMED` otherwise (R5).
6. In one transaction, `ReservationRepository` inserts the reservation and `NotificationService` adds the notification. The database exclusion constraint refuses a parallel overlapping insert (NFR-08).
7. The controller maps the record to `ReservationDto` and answers `201`. On any `DomainError`, the error handler answers with the error format of 5.8.4.3.

The sequence diagrams in 5.7 (Enes) show this flow and the check-in and no-show flows in UML.

#### System Scheduler

The System Scheduler (actor in the project card, UC-09) is a timer inside the backend process that runs the jobs J1–J4 every 60 seconds (5.8.4.9). It uses the same services and repositories as the HTTP side, so a rule is written once. The jobs are safe to repeat (conditional updates) and catch up after a restart.

#### Cross-cutting concerns

| Concern | Where | Decision |
|---|---|---|
| Authentication | `requireAuth` middleware | JWT, 1 hour (5.8.4.2). |
| Authorisation | `requireRole` middleware + ownership check in services | Server-side on every call (NFR-03). |
| Validation | `validate` middleware with zod schemas | Wrong input never reaches a service. |
| Error handling | One `errorHandler` at the end of the middleware chain | One error format for the whole API (5.8.4.3); stack traces only in the server log. |
| Time | Server clock, stored in UTC, business zone Europe/Istanbul | NFR-10. |
| Transactions | Services | One use case = one database transaction. |
| Configuration | Environment variables (`.env`, never committed) | `DATABASE_URL`, `JWT_SECRET`, `CORS_ORIGIN`, `PORT`. |
| Logging | Request log in the HTTP layer | Method, path, status, duration, user id. Never passwords, tokens or request bodies (details in 5.8.5). |

### 5.8.2 Technology stack

The stack itself was fixed by the team at the start (assumption C11 in 5.10). The table gives the reason for each choice and the alternative that was considered. "Version" is the version in `package.json` on `main`; for packages not installed yet it is the current release on the npm registry, checked on 23 Nov 2026.

| Layer | Technology | Version | Why it was chosen | Alternative considered |
|---|---|---|---|---|
| Language (both tiers) | TypeScript | 7.0 | One language for frontend and backend; the API types (`frontend/src/api/types.ts`) and the Prisma types catch a renamed field at compile time instead of in the demo. | JavaScript without types: less setup, but contract errors appear only at run time. |
| Frontend framework | React | 19.3 | Component model fits the screen list (12 pages); the frontend developer can reuse components across student and admin screens. | Vue or Angular: both would work; React was chosen because it is in the project plan the team agreed on (C11). |
| Frontend build tool | Vite | 8.3 | Fast development server and a static production build (`dist/`) that any static host can serve. | Next.js: adds server-side rendering, which the app does not need (all pages are behind login), and needs a Node.js host for the frontend. |
| Routing | React Router | 8.5 | Nested routes make the role guards simple (`RequireRole` around a group of routes). | Hand-written routing: no gain for 12 pages. |
| QR scanning in the browser | To be chosen by Enes. Candidates: `@zxing/browser` (0.2.1, last published 6 Jul 2026), `html5-qrcode` (2.3.8, last published 15 Apr 2023) | — | Must read a QR code with the phone camera over HTTPS and fall back to the 6-digit code (NFR-16). | The task document suggests `html5-qrcode`; its last release is from April 2023, so it should be tested on the team's phones before it is chosen. |
| QR code generation (admin) | `qrcode` | 1.5.4 | Draws the door QR code from `qrToken` in the admin screen so the admin can print it (FR-50). | A QR image stored on the server: more storage, no benefit. |
| Backend runtime | Node.js | ≥ 20.19 (`engines`) | Same language as the frontend; one person can read both tiers. | Java Spring Boot or Python Django: more structure, but a second language for a two-week build. |
| Web framework | Express | 5.3 (planned) | Small, well known, middleware model matches the layered design (auth → role → validate → controller → error handler). | NestJS: built-in modules and dependency injection, but more concepts to learn before the code freeze. Fastify: faster, but the team plan names Express. |
| Input validation | zod | 4.6 (planned) | Schemas in TypeScript; one schema gives both the check and the type. Named in Erol's task. | Joi or manual checks. |
| ORM | Prisma | 7.10.1 | Type-safe queries generated from the schema; migrations in the repository. Already used on `main`. | TypeORM, or raw SQL with `pg`: raw SQL gives full control but no generated types. |
| Database | PostgreSQL | 14 or newer | Relational data with foreign keys between the six tables; `timestamptz` for correct times; exclusion constraints with range types stop two overlapping reservations even under parallel requests (R3, NFR-08). | MySQL: no exclusion constraints, so R3 would need locking in the application. MongoDB: no foreign keys; the data is relational. |
| Authentication | JSON Web Token (`jsonwebtoken`) | 9.0 (planned) | Stateless: no session table, works the same on one or more server instances. | Server-side sessions with a cookie: easy logout, but needs a session store and CSRF protection. |
| Password hashing | bcryptjs | 3.0.3 | bcrypt in pure JavaScript; no native build step on the team's Windows machines. Already used in `seed.ts`. | `bcrypt` (native, faster) or Argon2. |
| Scheduler | `node-cron` or `setInterval` (Erol's choice) | node-cron 4.6 (planned) | Runs J1–J4 every 60 seconds inside the backend process; no extra service to deploy. | A separate worker process or a cloud cron calling an endpoint: survives the web server sleeping, but adds a second deployment (see 5.7 Deployment). |
| HTTP security middleware | helmet, cors, express-rate-limit | 8.3, 2.8, 8.7 (planned) | Security headers, only the frontend origin may call the API, login and check-in rate limits (5.8.4.6). | Writing the headers and limits by hand. |
| Tests | Vitest + Supertest (Görkem's choice between Vitest and Jest) | 5.1, 7.3 (planned) | Unit tests for R1–R9 in the Domain layer, API tests against Express without a browser; one command `npm test`. | Jest: also fits; the choice is the QA engineer's. |
| Lint | oxlint (frontend) | 1.90 | Comes with the current Vite template; no configuration needed. | ESLint. |
| Hosting (pilot and demo) | Vercel (frontend), Render (backend), Neon (PostgreSQL) | — | Free tiers for the pilot (5.11 Scenario A); all three serve over HTTPS, which the camera needs. | Paid plans (5.11 Scenario B); a university server (not available to the team). Details in 5.7 Deployment diagram. |
| Version control | Git + GitHub | — | Required deliverable (repository link); history shows who wrote what (5.13). | — |
