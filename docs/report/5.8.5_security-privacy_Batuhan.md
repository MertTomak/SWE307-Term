### 5.8.5.1 What we protect and from whom

| Asset | Why it matters | Main threat |
|---|---|---|
| Accounts and passwords | Anyone who logs in as another user can book, cancel or check in for that user. | Password guessing, stolen token. |
| `JWT_SECRET` | With the secret anyone can create a valid token for any role, including `RESOURCE_ADMIN`. | Secret committed to the repository or leaked from a log. |
| Door codes (`qrToken`, `checkInCode`) | The check-in is the only proof that the user is at the door (R7). If a student knows a code, he or she can check in from anywhere. | Code read through the API, or the 6-digit code guessed. |
| Reservation, check-in and penalty records | Personal data of students and staff (5.10.2). No-show counts lead to penalties (R9). | A user reads or changes another user's records. |
| The booking rules R1–R9 | They make the system fair: overlaps, limits and penalties. | A user skips a rule by calling the API directly, or by sending two requests at the same moment. |

**Who attacks.** The realistic attacker is a logged-in student who wants an advantage: more hours, a blocked slot, a check-in without going to the room, or no penalty. The second one is an outsider who tries passwords. The third risk is a team mistake, for example a committed secret or a debug output in production. We do not design against a strong attacker with access to the hosting provider; that is outside the scope of a student pilot.

**Main principle.** Every check runs on the server. The frontend hides buttons by role (`RequireRole`, H04), but this is only for the user's comfort, not a security control (NFR-03). The database enforces the most important invariants a second time (unique constraints, the R3 exclusion constraint, H02).

### 5.8.5.3 Authentication and passwords

The token rules are in 5.8.4.2. This part explains two choices.

**Password hashing: bcrypt, cost 10.** The OWASP Password Storage Cheat Sheet recommends Argon2id first, scrypt second, and says bcrypt "should only be used for password storage in legacy systems where Argon2 and scrypt are not available". For bcrypt it asks for "a work factor of 10 or more". We keep bcrypt for the pilot, for these reasons:
- Erol's seed script on `main` already uses `bcryptjs` with cost 10, so the stored hashes and the login code stay compatible.
- `bcryptjs` is plain JavaScript. It installs the same way on Windows (the team's computers) and on Render, so there is no build problem a week before the code freeze.
- Cost 10 meets the OWASP minimum.

This is a known deviation from the first OWASP choice. Moving to Argon2id is listed as future work. The move is smaller than it looks: Node.js has a built-in `crypto.argon2()` with the `argon2id` variant since v24.7.0 (Node.js crypto documentation), so on Node.js 24.7 or newer no extra package and no native build is needed. Whether the team moves to that Node.js version, and therefore whether Argon2id is used already in the pilot, is asked to Erol (H39). Because every hash stores its own algorithm and settings, the system can re-hash a user's password with the new algorithm at the next successful login.

**Password length 8 to 72 bytes (contract change).** The same cheat sheet says bcrypt has "a maximum length input length of 72 bytes for most implementations" and advises to enforce that maximum. Without a limit, two long passwords that start with the same 72 bytes would be treated as the same password. E01 therefore now accepts 8 to 72 bytes (UTF-8). The change is made in 5.8.4.2, E01 and API-A4.

**Why `sessionStorage` and not a cookie.** A token in `sessionStorage` can be read by a script that runs on our page, so the defence is to prevent script injection (A05: React escaping, no inline HTML from users). An `httpOnly` cookie would hide the token from scripts but would need CSRF protection and cross-site cookie settings between Vercel and Render, because the frontend and the API run on different domains. For a two-week build we chose the simpler model and limited the damage with a 1-hour lifetime (API-A1, API-A2).

### 5.8.5.4 Secrets and configuration

- `.env` and `.env.local` are listed in `.gitignore`. Only `.env.example` files with placeholder values are committed (README "How we work").
- Production values (`DATABASE_URL`, `JWT_SECRET`, `CORS_ORIGIN`, `SEED_PASSWORD`) are set in the Render environment settings. `VITE_API_URL` is set in Vercel (5.7 Deployment, Configuration).
- `JWT_SECRET` is created with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` and is different for local, demo and production.
- If a secret leaks: change it on Render and redeploy. All tokens signed with the old secret stop working at once; users log in again.

### 5.8.5.5 Data privacy: how the design meets KVKK

The legal analysis is in 5.10.2. This part does not re-interpret the law. It shows which technical measure answers each duty found there. Article 9 was not covered in 5.10.2. It was read for this section (source below).

|---|---|---|---|

**Logs are personal data too.** Server logs contain user ids, IP addresses and times. They follow the same rule: no passwords, tokens or door codes in them (A09), and they are kept only as long as Render keeps them by default. [TBD: check Render's log retention before real use.]

### 5.8.5.6 Security tests for 5.12

Görkem can turn these into automated tests (Vitest + Supertest) or manual checks. Each line names the expected answer from the API contract.

| ID | Test | Expected |
|---|---|---|
| ST-01 | Call `GET /reservations/me` without a token. | `401 UNAUTHENTICATED` |
| ST-02 | Call it with a token whose signature was changed, or that is older than 1 hour. | `401` |
| ST-03 | Student token calls `GET /admin/reservations/pending`. | `403 FORBIDDEN` |
| ST-04 | Student A asks for student B's reservation id (E09) or cancels it (E10). | `404 RESERVATION_NOT_FOUND` |
| ST-05 | Student calls `GET /resources/{id}`. | Body has no `qrToken` and no `checkInCode`. |
| ST-06 | Register with `role = RESOURCE_ADMIN`. | `400 VALIDATION_ERROR` |
| ST-07 | Six wrong logins for the same e-mail within 15 minutes. | 6th answer is `429 RATE_LIMITED` |
| ST-08 | Eleven wrong 6-digit codes by one user within 5 minutes. | 11th answer is `429 RATE_LIMITED` |
| ST-09 | Log in with a wrong password, then with an unknown e-mail. | Both `401 INVALID_CREDENTIALS`, same message. |
| ST-10 | Read the `User` table after registration. | Only a bcrypt hash (starts with `$2`), no plain password. |
| ST-11 | Search with `q = ' OR 1=1 --`. | Normal empty or filtered result, no error, no extra rows. |
| ST-12 | Cause a server error (for example, stop the database). | `500` with `INTERNAL_ERROR` only, no stack trace. |
| ST-13 | Call the API from another origin in the browser. | Blocked by CORS. |
| ST-14 | Open the demo URL with `http://`. | Redirected to `https://` or refused (NFR-04). |
| ST-15 | Run `npm audit` in `frontend/` and `backend/`. | No high or critical finding, or each one explained. |

The exact error codes come from the catalogue in 5.8.4.3. If a code changes there, this table follows it.
