## 5.5 Size and Effort Estimate: Function Point Analysis (IFPUG) and Basic COCOMO

This section sizes CampusSlot with IFPUG Function Point Analysis (FPA), converts the size to lines of code, and estimates effort and schedule with Basic COCOMO (organic mode). The result is compared with the real plan: 7 people from kickoff, an eighth who joined later, and about 2.5 weeks. Sources were accessed on 23 Nov 2026.

**Inputs.** (1) The data model in `backend/prisma/schema.prisma` on `main` (ILF/EIF). (2) The use cases UC-01 to UC-10 and the features F1 to F8 of the project card (EI/EO/EQ). The business rules R1 to R9 are used as named in the schema comments and the project card. The first draft of the functional requirements (FR-01 to FR-55) is in `5.4_requirements_Mert.md`. The column "Related FR" uses its numbers. The list is the PM's draft and is not yet confirmed by Zeynep, so the mapping may change.

**Counting rules used.** Complexity matrices and weights (ILF 7/10/15, EIF 5/7/10, EI 3/4/6, EO 4/5/7, EQ 3/4/6), the DET/RET/FTR rules, the 14 general system characteristics and VAF = 0.65 + 0.01 × TDI follow the IFPUG method as summarised in [Function Point Analysis (FPA) Explained](https://msdbok.github.io/content/scope/estimates/fpa_explained.html) (a secondary source that adapts IFPUG 4.1-era material). The IFPUG Counting Practices Manual itself was not read. [TBD: check the matrices against the current IFPUG CPM before submission]

### 5.5.3 FPA Assumptions

Numbered FP1, FP2, … to keep them apart from the planning assumptions A1–A6 and the constraints C1–C12.

- **FP1** Every Prisma `model` is a candidate logical file. The application boundary is the CampusSlot web application and its API. The database is inside the boundary.
- **FP2** Technical columns are not DETs: the surrogate `id` (UUID) and `updatedAt`. `createdAt` is counted only when a user sees it (Notification). Foreign keys are DETs, because they hold a relationship the user recognises (a reservation belongs to a user and a resource).
- **FP3** A column whose type is an enum (`role`, `type`, `status`, `method`) is **one** DET. The enum values are not counted one by one.
- **FP4** A RET is a user-recognisable subgroup inside a logical file. A model that only exists as a mandatory child of another model, is created with it and is deleted with it (`onDelete: Cascade`, `@unique` 1:1) is counted as a RET of the parent, not as its own ILF. `CheckIn` is therefore a RET of the Reservation ILF. Optional attribute groups that apply to only some records (the equipment approval decision, R5) are a RET. Sensitivity: if `CheckIn` were a separate ILF, UFP would be 114 instead of 107 (+7).
- **FP5** `Penalty` and `Notification` have `onDelete: Cascade` from `User`, but each has its own screens and rules (penalty list and R4/R9, notification list). They are independent ILFs.
- **FP6** There is no EIF. Constraint C10 says no data is imported from other university systems, and the schema has no externally maintained table.
- **FP7** DET rule for transactions: each input or output field counts once; the action control (button or command) counts once; all error and confirmation messages together count once. The `id` of a record the user selects counts as one DET. Values taken from the JWT (who is calling) are not user input and are not counted.
- **FP8** FTR = number of ILFs the transaction reads or writes. A RET inside an ILF does not add an FTR.
- **FP9** Role-based authorisation (F1) is a check inside every transaction. It is not a separate elementary process. The session/JWT token is not stored in an ILF.
- **FP10** Log in is an EQ: it only retrieves the User record and returns a token. It maintains no ILF.
- **FP11** At registration the user chooses STUDENT or ACADEMIC_STAFF. RESOURCE_ADMIN accounts are created by seed data, not through the UI (FR-02). [TBD: confirm with Zeynep]
- **FP12** Search (UC-02) filters by free text (name/location), type and minimum capacity, which are the searchable fields in the `Resource` model. The same transaction serves students and admins, so it is counted once.
- **FP13** The availability calendar is an EO because free/busy slots are derived from reservations. They are not stored.
- **FP14** QR scan and the typed 6-digit code (UC-05) are two ways to enter the same elementary process (same logic, same files). They are counted as one EI with both input DETs.
- **FP15** Approve and reject (UC-06) are one EI with a decision field and an optional rejection reason.
- **FP16** The no-show and penalty job (R8, R9, UC-09) is one system-triggered EO: it derives NO_SHOW status and the 3-in-30-days penalty and sends notifications. A clock trigger carries no data, so it is not counted as an EI.
- **FP17** Resources are deactivated through the update transaction (`isActive`), not deleted (schema comment, F8). There is no delete transaction.
- **FP18** `qrToken` and `checkInCode` are generated by the system, not typed by the admin.
- **FP19** "Mark notification as read" is counted because the schema has `Notification.isRead`. The project card text says only "in-app notifications". The requirement is FR-29 (priority Should in 5.4). [TBD: confirm with Zeynep that it is a requirement]
- **FP20** One person-month = 4.345 calendar weeks of full-time work (52.14 weeks / 12). The team capacity in section 5.5.8 assumes full-time work by the 7 members present from kickoff; the eighth member (Yağız Asker) is counted pro rata from a provisional join date of 26 Nov, 11 of the 19 project days (see 5.11, C17). Real weekly hours per member are not recorded. [TBD: team availability; confirm the join date]
- **FP21** QSM publishes no TypeScript row. The JavaScript row is used as the nearest language (see 5.5.7).
- **FP22** Auto-complete (`CHECKED_IN` becomes `COMPLETED` after the end time, FR-38) is not counted. The System Scheduler job only changes a status. No data crosses the boundary and nothing is sent to the user, so it is not an elementary process of its own (same reasoning as FP16 for the clock trigger). It is extra processing logic of the scheduler and does not change the DETs of #11.
- **FP23** Auto-reject of an `EQUIPMENT` reservation that is not decided by its start time (FR-55, decision D4 in 5.4.2a) is counted as its own EO (#19). It has a different business purpose from the no-show and penalty job (#11) and it sends a notification to the user. DET: `reservationId`, notification `type`, `message`, system `rejectionReason` = 4; FTR: Reservation, Notification = 2; EO matrix: Low = 4 FP. If the team decides it is part of #11, UFP is 103 instead of 107.
- **FP24** The end date of the user's penalty (FR-43) is shown as a banner on "My reservations" and is not a separate screen. It adds one DET (`endsAt`) and one FTR (Penalty) to #7. #7 has then 10 DET and 3 FTR, which is still Average (4 FP). If Arzum designs it as its own screen, it would be a separate EQ (Low, 3 FP). [TBD: confirm with Arzum]

### 5.5.8 Basic COCOMO (Organic Mode)

Formulas given by the project: E = 2.4 × KLOC^1.05 person-months; D = 2.5 × E^0.38 months; People = E / D. These are the organic-mode constants of Basic COCOMO in Boehm, B. W. (1981), *Software Engineering Economics*, Prentice-Hall. Organic mode is chosen because the team is small, the problem is well understood and the requirements are stable (the project card fixes F1–F8 and R1–R9). Basic COCOMO has no cost drivers, so team experience, tools and schedule pressure are not modelled.

| Case | KLOC | E (person-months) | D (months) | People = E/D |
|---|---|---|---|---|
| Low | 3.22 | 8.19 | 5.56 | 1.47 |
| Average | 4.88 | 12.67 | 6.56 | 1.93 |
| **Base** | **5.50** | **14.38** | **6.88** | **2.09** |
| High | 6.54 | 17.24 | 7.38 | 2.34 |

Base case worked: KLOC = 103.79 × 53 / 1000 = 5.501. E = 2.4 × 5.501^1.05 = 14.38 PM. D = 2.5 × 14.38^0.38 = 6.88 months. People = 14.38 / 6.88 = 2.09.

**Comparison with the real plan (FP20).** The plan is 7 people for about 2.5 weeks plus an eighth member for 11/19 of that time (the PERT plan in 5.5.2 uses 19 calendar days, 18 Nov–6 Dec; 2.5 weeks is the working-time figure given for this analysis).

| | COCOMO (base) | Real plan | Ratio |
|---|---|---|---|
| Effort | 14.4 person-months | 7 × 2.5 weeks + 1 × 2.5 × 11/19 weeks = 17.5 + 1.45 = 18.95 person-weeks = **4.4 person-months** | COCOMO is 3.3× the plan |
| Schedule | 6.9 months (29.9 weeks) | 2.5 weeks = 0.58 months | COCOMO is 12.0× the plan |
| Team size | 2.1 people | 8 people (7 from kickoff, 1 joined later) | plan is 3.8× larger |

With 19 calendar days instead of 2.5 weeks the plan has (7 × 19 + 11) / 30.44 = 4.7 person-months, and the ratios become 3.0× (effort) and 11.0× (schedule). (Before the eighth member was added the figures were 4.0 and 4.4 person-months and 3.6× and 3.3×.) The conclusion does not change. Even with the most favourable QSM ratio (31 LOC/FP, E = 8.2 PM) the plan has only about half of the COCOMO effort.

**Interpretation.**
1. The plan is far more compressed than the model. To finish 14.4 PM of work in 2.5 weeks, 25 people would be needed (14.4 PM / 0.575 months). A larger team does not give the same output as a longer schedule, so the plan cannot be reached just by adding people. Conversely, the plan's 4.4 PM corresponds, in the same formula, to about 1.8 KLOC, which is 32% of the estimated 5.5 KLOC (about 33 AFP at 53 LOC/FP).
2. The gap means that the plan and the estimated size do not fit each other. The 5.5 KLOC is the full F1–F8 scope written by hand to production level, and the 3.6× effort gap is measured against a model calibrated on professional projects.
3. Factors that can make the real effort lower than COCOMO's are plausible but not measured here: the stack uses generators and libraries (Prisma schema, migration and client; Vite; Express), and the schema, migration and seed already exist on `main`. Factors that can make it higher: the team learns the stack while working (5.10, team skills [TBD]), members work part-time next to other courses (FP20), and integration, testing and report writing are not in the LOC count.
4. Basic COCOMO was not validated against student projects, and the AFP count rests on assumptions FP1–FP24 and on a judgement-based TDI. The numbers are an order-of-magnitude check, not a prediction.
5. What this means for the plan: scope control matters more than adding people. The Scrum plan already fixes a code freeze on 1 Dec and limits the last week to blocker fixes (5.5.1, A4). Proposed cut order if time runs out: the two reports (#17, #18) first, then the availability calendar view (#4) is simplified to a list. The final order is to be confirmed by the Product Owner (Zeynep).

## Closing Notes (for the presentation)

### One-minute summary

We measured CampusSlot in function points with the IFPUG method. The five tables in our Prisma schema give 35 points of data functions, and the 19 transactions from the use cases and the first requirements list give 72 points, so the unadjusted count is 107. After scoring the 14 system characteristics at a total of 32, the value adjustment factor is 0.97 and the adjusted size is about 104 function points. QSM has no TypeScript ratio, so we used its JavaScript median of 53 lines per function point, which gives about 5.5 thousand lines of code. Basic COCOMO in organic mode then gives 14.4 person-months, 6.9 months and about 2 people. Our real plan has 7 people for about 2.5 weeks plus an eighth who joined later, which is about 4.4 person-months. So the plan has about 30% of the model's effort in about one twelfth of the time. We read this as a warning, not a forecast: the model has no cost drivers and was not built for student teams, but it tells us that scope control and the code freeze matter more than adding people. All assumptions are numbered FP1 to FP24, and each transaction is linked to the functional requirements in 5.4 (a first draft that Zeynep has not yet confirmed).

### Five likely questions from the instructor

**1. Why did you use the JavaScript ratio for a TypeScript project?**
QSM's table, release 5.0, has no TypeScript row. QSM's own guidance says to substitute a comparable language and widen the uncertainty. We used the JavaScript median (53) and show the full QSM range (31 to 63 LOC/FP), which moves effort between 8.2 and 17.2 person-months. TypeScript's type annotations may push the real ratio up, so the base case could be slightly low.

**2. Why is every ILF Low, and why is CheckIn not its own file?**
All five files have fewer than 20 DETs and at most three RETs, so the IFPUG matrix gives Low (7 FP). We treated CheckIn as a RET of Reservation because it is one-to-one, mandatory, created with the reservation process and deleted with it (cascade). If it were counted as an ILF, UFP would be 114 instead of 107 and the AFP would be about 111. Assumption FP4 records this.

**3. How much do your general system characteristic scores matter?**
Little. VAF can only range from 0.65 to 1.35, so AFP stays between 70 and 144 for any scores. Our TDI of 32 gives VAF 0.97, which changes the size by 3%. We re-checked GSC 3, 4, 5 and 12 against the proposed non-functional targets and no score changed. The size depends far more on the counting assumptions (FP1 to FP24) and on the LOC/FP ratio than on the scores.

**4. Your plan has about 4.4 person-months and COCOMO says 14.4. Is the project infeasible?**
Not necessarily, but the plan is at high risk. Basic COCOMO has no cost drivers and was not calibrated on student teams. Libraries and generators (Prisma, Express, Vite) and the existing schema and seed reduce the hand-written code, while learning the stack, part-time availability and integration work increase the effort. The model says the schedule is about 12 times shorter than nominal, and adding people does not fix that, because 14.4 person-months in 2.5 weeks would need 25 people. Our response is scope control: a fixed code freeze on 1 December, blocker-only fixes afterwards, and a proposed cut order for features, to be confirmed by the Product Owner.

**5. How reliable is a function point count? Can you link it to requirements?**
The count depends on the counter's decisions, so we wrote 24 assumptions. We did not use the IFPUG manual itself, only a secondary summary, which is marked [TBD] in the text. The "Related FR" column links all 19 transactions to the 55 functional requirements of the first draft in 5.4. The draft is not yet confirmed by Zeynep. FRs with no transaction (log out, auto-complete) show where the count and the requirements differ, and we explain each one in FP22 and 5.4.5.
