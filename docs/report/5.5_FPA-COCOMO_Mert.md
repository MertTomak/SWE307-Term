## 5.5 Size and Effort Estimate: Function Point Analysis (IFPUG) and Basic COCOMO

This section sizes CampusSlot with IFPUG Function Point Analysis (FPA), converts the size to lines of code, and estimates effort and schedule with Basic COCOMO (organic mode). The result is compared with the real plan: 7 people and about 2.5 weeks. Sources were accessed on 23 Nov 2026.

**Inputs.** (1) The data model in `backend/prisma/schema.prisma` on `main` (ILF/EIF). (2) The use cases UC-01 to UC-10 and the features F1 to F8 of the project card (EI/EO/EQ). The business rules R1 to R9 are used as named in the schema comments and the project card. Zeynep's FR list does not exist yet, so the column "Related FR" is `[to be mapped]` for every transaction.

**Counting rules used.** Complexity matrices and weights (ILF 7/10/15, EIF 5/7/10, EI 3/4/6, EO 4/5/7, EQ 3/4/6), the DET/RET/FTR rules, the 14 general system characteristics and VAF = 0.65 + 0.01 × TDI follow the IFPUG method as summarised in [Function Point Analysis (FPA) Explained](https://msdbok.github.io/content/scope/estimates/fpa_explained.html) (a secondary source that adapts IFPUG 4.1-era material). The IFPUG Counting Practices Manual itself was not read. [TBD: check the matrices against the current IFPUG CPM before submission]

### 5.5.3 FPA Assumptions

Numbered FP1, FP2, … to keep them apart from the planning assumptions A1–A5 and the constraints C1–C11.

- **FP1** Every Prisma `model` is a candidate logical file. The application boundary is the CampusSlot web application and its API. The database is inside the boundary.
- **FP2** Technical columns are not DETs: the surrogate `id` (UUID) and `updatedAt`. `createdAt` is counted only when a user sees it (Notification). Foreign keys are DETs, because they hold a relationship the user recognises (a reservation belongs to a user and a resource).
- **FP3** A column whose type is an enum (`role`, `type`, `status`, `method`) is **one** DET. The enum values are not counted one by one.
- **FP4** A RET is a user-recognisable subgroup inside a logical file. A model that only exists as a mandatory child of another model, is created with it and is deleted with it (`onDelete: Cascade`, `@unique` 1:1) is counted as a RET of the parent, not as its own ILF. `CheckIn` is therefore a RET of the Reservation ILF. Optional attribute groups that apply to only some records (the equipment approval decision, R5) are a RET. Sensitivity: if `CheckIn` were a separate ILF, UFP would be 110 instead of 103 (+7).
- **FP5** `Penalty` and `Notification` have `onDelete: Cascade` from `User`, but each has its own screens and rules (penalty list and R4/R9, notification list). They are independent ILFs.
- **FP6** There is no EIF. Constraint C10 says no data is imported from other university systems, and the schema has no externally maintained table.
- **FP7** DET rule for transactions: each input or output field counts once; the action control (button or command) counts once; all error and confirmation messages together count once. The `id` of a record the user selects counts as one DET. Values taken from the JWT (who is calling) are not user input and are not counted.
- **FP8** FTR = number of ILFs the transaction reads or writes. A RET inside an ILF does not add an FTR.
- **FP9** Role-based authorisation (F1) is a check inside every transaction. It is not a separate elementary process. The session/JWT token is not stored in an ILF.
- **FP10** Log in is an EQ: it only retrieves the User record and returns a token. It maintains no ILF.
- **FP11** At registration the user chooses STUDENT or ACADEMIC_STAFF. RESOURCE_ADMIN accounts are created by seed data, not through the UI. [TBD: confirm with Zeynep]
- **FP12** Search (UC-02) filters by free text (name/location), type and minimum capacity, which are the searchable fields in the `Resource` model. The same transaction serves students and admins, so it is counted once.
- **FP13** The availability calendar is an EO because free/busy slots are derived from reservations. They are not stored.
- **FP14** QR scan and the typed 6-digit code (UC-05) are two ways to enter the same elementary process (same logic, same files). They are counted as one EI with both input DETs.
- **FP15** Approve and reject (UC-06) are one EI with a decision field and an optional rejection reason.
- **FP16** The no-show and penalty job (R8, R9, UC-09) is one system-triggered EO: it derives NO_SHOW status and the 3-in-30-days penalty and sends notifications. A clock trigger carries no data, so it is not counted as an EI.
- **FP17** Resources are deactivated through the update transaction (`isActive`), not deleted (schema comment, F8). There is no delete transaction.
- **FP18** `qrToken` and `checkInCode` are generated by the system, not typed by the admin.
- **FP19** "Mark notification as read" is counted because the schema has `Notification.isRead`. The project card text says only "in-app notifications". [TBD: confirm with Zeynep that it is a requirement]
- **FP20** One person-month = 4.345 calendar weeks of full-time work (52.14 weeks / 12). The team capacity in section 5.5.8 assumes full-time work by all 7 members. Real weekly hours per member are not recorded. [TBD: team availability]
- **FP21** QSM publishes no TypeScript row. The JavaScript row is used as the nearest language (see 5.5.7).

### 5.5.8 Basic COCOMO (Organic Mode)

Formulas given by the project: E = 2.4 × KLOC^1.05 person-months; D = 2.5 × E^0.38 months; People = E / D. These are the organic-mode constants of Basic COCOMO in Boehm, B. W. (1981), *Software Engineering Economics*, Prentice-Hall. Organic mode is chosen because the team is small, the problem is well understood and the requirements are stable (the project card fixes F1–F8 and R1–R9). Basic COCOMO has no cost drivers, so team experience, tools and schedule pressure are not modelled.

| Case | KLOC | E (person-months) | D (months) | People = E/D |
|---|---|---|---|---|
| Low | 3.10 | 7.87 | 5.47 | 1.44 |
| Average | 4.70 | 12.18 | 6.46 | 1.88 |
| **Base** | **5.30** | **13.81** | **6.78** | **2.04** |
| High | 6.29 | 16.56 | 7.26 | 2.28 |

Base case worked: KLOC = 99.91 × 53 / 1000 = 5.295. E = 2.4 × 5.295^1.05 = 13.81 PM. D = 2.5 × 13.81^0.38 = 6.78 months. People = 13.81 / 6.78 = 2.04.

**Comparison with the real plan (FP20).** The plan is 7 people for about 2.5 weeks (the PERT plan in 5.5.2 uses 19 calendar days, 18 Nov–6 Dec; 2.5 weeks is the working-time figure given for this analysis).

| | COCOMO (base) | Real plan | Ratio |
|---|---|---|---|
| Effort | 13.8 person-months | 7 × 2.5 weeks = 17.5 person-weeks = **4.0 person-months** | COCOMO is 3.4× the plan |
| Schedule | 6.8 months (29.5 weeks) | 2.5 weeks = 0.58 months | COCOMO is 11.8× the plan |
| Team size | 2.0 people | 7 people | plan is 3.4× larger |

With 19 calendar days instead of 2.5 weeks the plan has 4.4 person-months, and the ratios become 3.2× (effort) and 10.9× (schedule). The conclusion does not change. Even with the most favourable QSM ratio (31 LOC/FP, E = 7.9 PM) the plan has only about half of the COCOMO effort.

**Interpretation.**
1. The plan is far more compressed than the model. To finish 13.8 PM of work in 2.5 weeks, 24 people would be needed (13.8 PM / 0.575 months). A larger team does not give the same output as a longer schedule, so the plan cannot be reached just by adding people. Conversely, the plan's 4.0 PM corresponds, in the same formula, to about 1.6 KLOC, which is 31% of the estimated 5.3 KLOC (about 31 AFP at 53 LOC/FP).
2. The gap means that the plan and the estimated size do not fit each other. The 5.3 KLOC is the full F1–F8 scope written by hand to production level, and the 3.4× effort gap is measured against a model calibrated on professional projects.
3. Factors that can make the real effort lower than COCOMO's are plausible but not measured here: the stack uses generators and libraries (Prisma schema, migration and client; Vite; Express), and the schema, migration and seed already exist on `main`. Factors that can make it higher: the team learns the stack while working (5.10, team skills [TBD]), members work part-time next to other courses (FP20), and integration, testing and report writing are not in the LOC count.
4. Basic COCOMO was not validated against student projects, and the AFP count rests on assumptions FP1–FP21 and on a judgement-based TDI. The numbers are an order-of-magnitude check, not a prediction.
5. What this means for the plan: scope control matters more than adding people. The Scrum plan already fixes a code freeze on 1 Dec and limits the last week to blocker fixes (5.5.1, A4). If time runs out, features need a cut order, for example the two reports (#17, #18, 10 FP together). ## Closing Notes (for the presentation)

### One-minute summary

We measured CampusSlot in function points with the IFPUG method. The five tables in our Prisma schema give 35 points of data functions, and the 18 transactions from the use cases give 68 points, so the unadjusted count is 103. After scoring the 14 system characteristics at a total of 32, the value adjustment factor is 0.97 and the adjusted size is about 100 function points. QSM has no TypeScript ratio, so we used its JavaScript median of 53 lines per function point, which gives about 5.3 thousand lines of code. Basic COCOMO in organic mode then gives 13.8 person-months, 6.8 months and about 2 people. Our real plan has 7 people for about 2.5 weeks, which is about 4 person-months. So the plan has roughly one third of the model's effort in about one twelfth of the time. We read this as a warning, not a forecast: the model has no cost drivers and was not built for student teams, but it tells us that scope control and the code freeze matter more than adding people. All assumptions are numbered FP1 to FP21 and the functional requirement mapping waits for Zeynep's list.

### Five likely questions from the instructor

**1. Why did you use the JavaScript ratio for a TypeScript project?**
QSM's table, release 5.0, has no TypeScript row. QSM's own guidance says to substitute a comparable language and widen the uncertainty. We used the JavaScript median (53) and show the full QSM range (31 to 63 LOC/FP), which moves effort between 7.9 and 16.6 person-months. TypeScript's type annotations may push the real ratio up, so the base case could be slightly low.

**2. Why is every ILF Low, and why is CheckIn not its own file?**
All five files have fewer than 20 DETs and at most three RETs, so the IFPUG matrix gives Low (7 FP). We treated CheckIn as a RET of Reservation because it is one-to-one, mandatory, created with the reservation process and deleted with it (cascade). If it were counted as an ILF, UFP would be 110 instead of 103 and the AFP would be about 107. Assumption FP4 records this.

**3. How much do your general system characteristic scores matter?**
Little. VAF can only range from 0.65 to 1.35, so AFP stays between 67 and 139 for any scores. Our TDI of 32 gives VAF 0.97, which changes the size by 3%. The size depends far more on the counting assumptions (FP1 to FP21) and on the LOC/FP ratio than on the scores.

**4. Your plan has 4 person-months and COCOMO says 13.8. Is the project infeasible?**
Not necessarily, but the plan is at high risk. Basic COCOMO has no cost drivers and was not calibrated on student teams. Libraries and generators (Prisma, Express, Vite) and the existing schema and seed reduce the hand-written code, while learning the stack, part-time availability and integration work increase the effort. The model says the schedule is about 12 times shorter than nominal, and adding people does not fix that, because 13.8 person-months in 2.5 weeks would need 24 people. Our response is scope control: a fixed code freeze on 1 December, blocker-only fixes afterwards, and a priority order for features. The risk is still to be written into the risk register.

**5. How reliable is a function point count? Can you link it to requirements?**
The count depends on the counter's decisions, so we wrote 21 assumptions. The page we used for the counting rules notes that trained counters differ by a median of 12% (it cites Kemerer, 1993; we did not read the original). We did not use the IFPUG manual itself, only a secondary summary, which is marked [TBD] in the text. The "Related FR" column is `[to be mapped]` for all 18 transactions because the functional requirements list does not exist yet. Once it does, each FR will map to one or more transactions, and any FR that has no transaction shows a gap in the count.
