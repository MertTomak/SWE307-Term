A change to this contract is made through a pull request that the System Architect reviews, so that the backend and the frontend never drift apart.

### 5.8.4.1 General conventions

| Topic | Decision | Reason |
|---|---|---|
| Style | REST over HTTPS, JSON in UTF-8. | One web client and one server; REST is the style the whole team knows (see 5.8 technology stack). HTTPS is required for camera access in the browser (NFR-04). |
| Base path | `/api/v1` | A later breaking change can be published as `/api/v2` without breaking the deployed client. |
| Resource names | Plural nouns (`/resources`, `/reservations`). | Common REST convention; easy to read in the endpoint table. |
| State changes | Modelled as action sub-resources with `POST`, for example `POST /reservations/{id}/cancel`. A reservation is never deleted. | Every state change is a guarded transition of the Reservation state machine (State pattern, 5.7). Cancelled, rejected and no-show records must stay in the database for R9 and for the reports in UC-08. |
| IDs | UUID strings. | Schema uses `@default(uuid())`. UUIDs cannot be guessed by counting. |
| Field names | camelCase, identical to the Prisma fields. | No mapping layer is needed between the database, the API and the client. |
| Enum values | Exactly as in the project card (`STUDENT`, `CONFIRMED`, `EQUIPMENT`, …). | Keeps the eight team members' outputs consistent. |
| Time format | ISO 8601 with an offset, for example `2026-11-25T14:00:00+03:00`. A timestamp without an offset is refused with `400 VALIDATION_ERROR`. **Responses** always give times in UTC with the suffix `Z` (for example `2026-11-25T11:00:00.000Z`); `Z` is the offset +00:00, and the client shows the time in Europe/Istanbul (confirmed 27 Nov, H49 point 5). | Without an offset the server cannot know which moment the client meant. |
| Time storage | The database stores UTC (`timestamptz`). | Schema uses `@db.Timestamptz(3)`. |
| Business time zone | `Europe/Istanbul` (IANA time zone name). Dates without a time (for example `date=2026-11-25` in the availability query, `from`/`to` in reports) are read as calendar days in this zone. The client shows all times in this zone. | Resolves NFR-10. The campus is in Istanbul. |
| Clock | R6, R7, R8 and R9 are checked only with the server clock, never with a time sent by the client. | NFR-10. A wrong phone clock must not open or close the check-in window. |

### 5.8.4.2 Authentication and authorisation (JWT)

1. `POST /api/v1/auth/register` and `POST /api/v1/auth/login` return an access token.
2. The client sends it on every protected call in the header `Authorization: Bearer <token>`.
3. The token is a JSON Web Token signed with HS256. The secret is read from the environment variable `JWT_SECRET` and is never committed to the repository (`.env` is in `.gitignore`).
4. Claims: `sub` (user id), `role` (`STUDENT`, `ACADEMIC_STAFF` or `RESOURCE_ADMIN`), `iat`, `exp`.
5. Lifetime: 1 hour (NFR-02). There is no refresh token (assumption API-A1). After expiry the client receives `401 TOKEN_EXPIRED` and sends the user to the login page.
6. Log out (FR-06) is done in the client by deleting the token. There is no server endpoint, because the token is stateless. The token stays valid until it expires; with a 1-hour lifetime this is accepted (API-A2).
7. The client keeps the token in `sessionStorage`, so it is removed when the browser tab is closed (API-A3).
8. Every protected route passes two middleware functions in this order: `requireAuth` (token present, signature valid, not expired → otherwise `401`) and `requireRole(...roles)` (role allowed → otherwise `403 FORBIDDEN`). The role is checked on the server for every call; hiding a button in the client is not enough (NFR-03).
9. Passwords are hashed with bcrypt, cost factor 10 (the same value as `backend/prisma/seed.ts`). The plain password is never stored or logged (NFR-01). Password length: at least 8 characters and at most 72 bytes in UTF-8, because bcrypt reads only the first 72 bytes (API-A4, 5.8.5.3).

### 5.8.4.3 Error format

Every error response has the same body, whatever the endpoint:

```json
{
  "error": {
    "code": "RULE_R2_ACTIVE_LIMIT",
    "message": "You already have 2 active reservations. A student can have at most 2.",
    "rule": "R2",
    "details": { "limit": 2, "active": 2 }
  }
}
```

| Field | Always present? | Meaning |
|---|---|---|
| `code` | Yes | Stable, machine-readable code from the catalogue below. The client decides what to show by `code`, never by `message`. |
| `message` | Yes | One English sentence in plain words for the user (FR-21, FR-37). |
| `rule` | Only for business-rule errors | `R1` … `R9`, so the user and the tester see which rule failed. |
| `details` | No | Extra data. For `VALIDATION_ERROR`: `{ "fields": [ { "path": "endTime", "message": "Required" } ] }` built from the zod error. |

**HTTP status codes used.**

| Status | Used when |
|---|---|
| 200 OK | Read or update succeeded. |
| 201 Created | A new record was created (user, reservation, check-in, resource). |
| 400 Bad Request | The request body or query does not match the schema (zod validation). |
| 401 Unauthorized | No token, invalid token, expired token, or wrong login credentials. |
| 403 Forbidden | Logged in, but the role is not allowed to call this endpoint. |
| 404 Not Found | The record does not exist, or it belongs to another user (see 5.8.4.6). |
| 409 Conflict | The request clashes with the current data: overlap (R3), e-mail already used, invalid state transition, already checked in. |
| 422 Unprocessable Content | The request is valid, but a business rule refuses it (R1, R2, R4, R6, R7, start in the past, resource inactive). |
| 429 Too Many Requests | Rate limit reached (login, check-in). |
| 500 Internal Server Error | Unexpected error. The body contains `INTERNAL_ERROR` only; the stack trace is written to the server log and never sent to the client. |

### 5.8.4.4 Pagination

Every list endpoint accepts `page` (default 1) and `pageSize` (default 20, maximum 100) and answers with:

```json
{ "data": [ ... ], "page": 1, "pageSize": 20, "total": 57 }
```

The sort order is fixed per endpoint and written in the endpoint table. Client-chosen sorting is out of scope (API-A5).

### 5.8.4.5 Data transfer objects (DTOs)

The API never returns a Prisma record as it is. Each endpoint returns one of these shapes.

| DTO | Fields | Note |
|---|---|---|
| `UserDto` | `id`, `email`, `fullName`, `role` | `passwordHash` is never sent. |
| `ResourceDto` | `id`, `name`, `type`, `location`, `capacity`, `description`, `isActive` | Seen by every logged-in user. **No door codes.** |
| `AdminResourceDto` | `ResourceDto` + `qrToken`, `checkInCode`, `createdAt`, `updatedAt` | Only for `RESOURCE_ADMIN`; used to print the door QR code. |
| `ReservationDto` | `id`, `resource` {`id`, `name`, `type`, `location`}, `startTime`, `endTime`, `status`, `purpose`, `rejectionReason`, `decidedAt`, `cancelledAt`, `checkIn` ({`checkedInAt`, `method`} or `null`), `createdAt` | |
| `AdminReservationDto` | `ReservationDto` + `user` {`id`, `fullName`, `email`} | Only in admin endpoints. |
| `NotificationDto` | `id`, `type`, `message`, `reservationId`, `isRead`, `createdAt` | |
| `PenaltyDto` | `id`, `user` {`id`, `fullName`, `email`}, `reason`, `noShowCount`, `startsAt`, `endsAt` | Only in admin endpoints. |
| `Page<T>` | `data: T[]`, `page`, `pageSize`, `total` | See 5.8.4.4. |

**Why the door codes are hidden.** If a Student could read `qrToken` or `checkInCode` through the API, he or she could check in from anywhere, and the QR check-in would no longer prove that the user is at the door (R7). The codes are therefore only in `AdminResourceDto`.

**Rate limits.** `POST /auth/login`: at most 5 failed attempts per e-mail and IP in 15 minutes. `POST /check-ins`: at most 10 failed attempts per user in 5 minutes. Both answer `429 RATE_LIMITED`. The second limit stops a user from guessing 6-digit door codes (API-A6). Behind the Render proxy the server must know the real client IP, so the backend runs with `TRUST_PROXY=1` there (H49 point 7, 5.7 Deployment).

### 5.8.4.7 Reservation rule chain (E07)

The ReservationService runs the checks below in this fixed order and stops at the first failure (Strategy pattern, 5.7: each rule is its own validator class). Cheap checks without database access come first; the overlap check comes last because it runs inside the transaction.

| Step | Check | Fails with | Source |
|---|---|---|---|
| 0a | Body matches the zod schema; timestamps have an offset. | `400 VALIDATION_ERROR` | — |
| 0b | Role is `STUDENT` or `ACADEMIC_STAFF`. | `403 FORBIDDEN` | D3 |
| 0c | `endTime` > `startTime`; `startTime` ≥ server time. | `422 INVALID_TIME_RANGE` / `422 START_IN_PAST` | FR-20 |
| 0d | Resource exists and `isActive = true`. | `404 RESOURCE_NOT_FOUND` / `422 RESOURCE_INACTIVE` | FR-11 |
| 1 | **R1** `endTime − startTime ≤ 180 minutes`. Exactly 3 hours is allowed. | `422 RULE_R1_MAX_DURATION` | R1, FR-14 |
| 2 | **R4** no penalty with `startsAt ≤ now < endsAt`. | `422 RULE_R4_ACTIVE_PENALTY` | R4, FR-17 |
| 3 | **R2** active reservations < limit (Student 2, Academic Staff 5). Active = start in the future and status `PENDING_APPROVAL` or `CONFIRMED` (D1). | `422 RULE_R2_ACTIVE_LIMIT` | R2, D1, FR-15 |
| 4 | **R3** no reservation on the same resource with status `PENDING_APPROVAL`, `CONFIRMED` or `CHECKED_IN` where `existing.startTime < new.endTime` **and** `existing.endTime > new.startTime`. Back-to-back slots (10:00–11:00 and 11:00–12:00) do not overlap. | `409 RULE_R3_OVERLAP` | R3, D2, FR-16 |
| 5 | **R5** decides the status: `EQUIPMENT` → `PENDING_APPROVAL`; `ROOM`, `LAB` → `CONFIRMED`. This step never refuses. | — | R5, FR-18, FR-19 |
| 6 | Insert the reservation and a notification (`RESERVATION_CONFIRMED` or `RESERVATION_PENDING`). | — | FR-22 |

**Two users booking the same slot at the same moment (NFR-08).** Steps 3 to 6 run in one database transaction. A check in the application alone cannot stop two parallel requests that both see "free" before either inserts. The database must therefore refuse the second insert. Recommended: a PostgreSQL exclusion constraint on `Reservation` (`EXCLUDE USING gist (resourceId WITH =, tstzrange(startTime, endTime) WITH &&) WHERE status IN ('PENDING_APPROVAL','CONFIRMED','CHECKED_IN')`). Erol wrote such a guard on the branch `erol/prisma-schema`, but it is not in the migration merged to `main`. The API maps the PostgreSQL error for this constraint to `409 RULE_R3_OVERLAP`. Decision (System Architect, 23 Nov 2026): the guard is added back to `main` as a migration; Erol implements it.

### 5.8.4.8 Check-in logic (E11)

1. Find the resource: `QR_SCAN` → `Resource.qrToken = code`; `MANUAL_CODE` → `Resource.checkInCode = code`. None → `404 CHECKIN_CODE_INVALID`.
2. Find the caller's reservation on that resource with `status = CONFIRMED` and `startTime − 10 min ≤ now ≤ startTime + 15 min`. Both ends are inclusive, so a check-in at exactly 15:00 minutes after the start is accepted (R7).
3. Found → in one transaction create `CheckIn` (`method` from the request) and set the status to `CHECKED_IN`. Answer `201`.
4. Not found → answer with the reason (FR-37), checked in this order on the caller's reservations for this resource:
   - one is `CHECKED_IN` and has not ended → `409 ALREADY_CHECKED_IN`
   - one is `CONFIRMED` and starts more than 10 minutes from now (the nearest one) → `422 RULE_R7_TOO_EARLY` with `windowOpensAt`
   - one is `CONFIRMED` and its start was more than 15 minutes ago → `422 RULE_R7_TOO_LATE`
   - one is `PENDING_APPROVAL` → `422 RESERVATION_NOT_CONFIRMED`
   - otherwise → `404 NO_RESERVATION_HERE`

The window in step 2 and the no-show condition of the scheduler (5.8.4.9, J1: `startTime + 15 min < now`) use the same boundary, so a reservation can never be both "still open for check-in" and "no-show".

### 5.8.4.9 System Scheduler (UC-09, no HTTP endpoint)

**Run interval: every 60 seconds** (decided by the System Architect, 23 Nov 2026; resolves the open point in 5.4 F6 and the run interval in NFR-14). A no-show is therefore recorded at most about one minute after the 15-minute mark. The jobs run inside the backend process (for example with `node-cron` or `setInterval`; the library is Erol's choice).

| Job | Selects | Does | FR / rule |
|---|---|---|---|
| J1 NoShowJob | `status = CONFIRMED` and `startTime + 15 min < now` | Set `NO_SHOW`, notification `NO_SHOW_RECORDED`. Then for each affected user: if the user has ≥ 3 `NO_SHOW` with `startTime` in the last 30 days and no running penalty → create `Penalty` (`startsAt = now`, `endsAt = now + 7 days`, `noShowCount`) and notification `PENALTY_APPLIED`. | R8, R9, FR-39 – FR-42 |
| J2 CompleteJob | `status = CHECKED_IN` and `endTime ≤ now` | Set `COMPLETED`. | FR-38 |
| J3 AutoRejectJob | `status = PENDING_APPROVAL` and `startTime ≤ now` | Set `REJECTED`, `rejectionReason = "Not approved before the start time"`, `decidedById = null`, notification `RESERVATION_REJECTED`. | D4, FR-55 |
| J4 ReminderJob | `status = CONFIRMED` and `startTime − 10 min ≤ now < startTime` and no `CHECK_IN_REMINDER` yet for this reservation | Notification `CHECK_IN_REMINDER`. | FR-30 |

Order inside one run: J3, J1, J2, J4.

**No double processing, no missed reservation (NFR-14).** Each status change is a conditional update (`UPDATE … WHERE id = ? AND status = 'CONFIRMED'`). If another run already changed the row, zero rows are updated and the job skips it, so the same reservation is never processed twice. The conditions use "before now", not "exactly now", so reservations that were due while the server was stopped or asleep are handled at the first run after restart.

**Hosting note.** A backend on a free tier that sleeps when idle (5.11, Render free web service) also stops the scheduler. The catch-up rule above keeps the data correct, but no-shows are recorded late while it sleeps. This is handled in the deployment design (5.7 Deployment diagram).

R9 counts no-shows by the reservation's `startTime` (API-A7). Whether the no-shows that already caused a penalty are counted again for the next one is still open [TBD: Product Owner, 5.4 F6].

### 5.8.4.10 Report formulas (E20)

For each resource in the period [`from` 00:00, `to` 24:00] in Europe/Istanbul:

- `reservationCount` = number of reservations with status `CONFIRMED`, `CHECKED_IN`, `COMPLETED` or `NO_SHOW` that start in the period.
- `bookedHours` = sum of (`endTime − startTime`) of those reservations, in hours.
- `occupancyRate` = `bookedHours` ÷ (number of days in the period × daily opening hours). Daily opening hours = [TBD: Zeynep, ask in the admin interview] (API-A8).
- `noShowCount` = number of those reservations with status `NO_SHOW`.
- `noShowRate` = `noShowCount` ÷ (number with status `CHECKED_IN`, `COMPLETED` or `NO_SHOW`). If the divisor is 0, the rate is `null`.

### 5.8.4.12 Assumptions

| ID | Assumption |
|---|---|
| API-A1 | No refresh token. A user logs in again after 1 hour. This keeps the scope small for a two-week build. |
| API-A2 | Log out only deletes the token in the client. A stolen token stays valid until it expires (at most 1 hour). |
| API-A3 | The client keeps the token in `sessionStorage`. |
| API-A4 | Password length is 8 characters to 72 bytes (UTF-8). The upper limit comes from bcrypt (5.8.5.3, changed 24 Nov 2026). No other password rule is set. |
| API-A5 | Lists have a fixed sort order; the client cannot choose another one. |
| API-A6 | Rate-limit numbers (5 per 15 min for login, 10 per 5 min for check-in) are team proposals, not taken from a standard. |
| API-A7 | R9 counts a no-show by the reservation's `startTime`. To be confirmed by the Product Owner (5.4 F6 open point). |
| API-A8 | Daily opening hours for the occupancy rate are not known yet (H08). Until they are, the code uses `REPORT_OPENING_HOURS_PER_DAY`, default 12 hours (08:00–20:00), confirmed 27 Nov (H49 point 6). |
