### 5.6.5 Decision tables

A decision table lists every combination of conditions and the action the system takes for each one. With 5 conditions that are either true (Y) or false (N) there are 2^5 = 32 combinations, called rules. The full table proves that no combination was forgotten. The reduced table is the same logic in fewer rules: two rules that lead to the same action and differ in only one condition are merged, and that condition gets "–" (does not matter). Each reduced rule becomes at least one test case in 5.12.

**Notation.** Y = condition true, N = condition false, – = does not matter. Rules in the full tables are numbered 1–32; C1 changes slowest and C5 fastest, Y before N. Reduced rules are named DT1-1 … DT1-6 and DT2-1 … DT2-7 so that test cases can refer to them. The full tables are written with one rule per row (instead of one rule per column) so that 32 rules fit on a page.

#### DT-1 Reservation request evaluation (R1–R5, UC-03)

**Scope.** A reservation request (E07) that has already passed the input checks of the rule chain (5.8.4.7, steps 0a–0d): valid body, role `STUDENT` or `ACADEMIC_STAFF`, end after start, start not in the past, resource exists and is active. Those checks are not business rules R1–R5 and are covered by UC-03 alternative flows 2a, 3a, 4a and \*a.

**Conditions**

| ID | Condition | Rule | Y means |
|---|---|---|---|
| C1 | The user has a running penalty (`startsAt ≤ now < endsAt`). | R4 | Penalty running → must reject |
| C2 | The time slot is free on this resource: no reservation with the status `PENDING_APPROVAL`, `CONFIRMED` or `CHECKED_IN` overlaps it. Back-to-back slots count as free. | R3, D2 | Free |
| C3 | The duration is at most 3 hours (`endTime − startTime ≤ 180 min`). Exactly 3 hours counts as Y. | R1 | Allowed length |
| C4 | The active reservation limit is not reached (active < 2 for Student, < 5 for Academic Staff; active as defined in D1). | R2, D1 | Under the limit |
| C5 | The resource type is `EQUIPMENT`. | R5 | Needs admin approval |

**Actions**

| ID | Action | Result |
|---|---|---|
| A1 | Reject and name the rule that failed (FR-21). | `422 RULE_R1_MAX_DURATION`, `422 RULE_R4_ACTIVE_PENALTY`, `422 RULE_R2_ACTIVE_LIMIT` or `409 RULE_R3_OVERLAP`. No reservation is stored. |
| A2 | Create the reservation with the status `PENDING_APPROVAL`. | `201`, notification `RESERVATION_PENDING` (FR-19). |
| A3 | Create the reservation with the status `CONFIRMED`. | `201`, notification `RESERVATION_CONFIRMED` (FR-18). |

**Which reason is given when several rules fail.** The rule chain checks R1, R4, R2, R3 in this order and stops at the first failure (5.8.4.7). The reason in A1 is therefore the first failing rule in that order, not every failing rule. Example: rule 9 below has a running penalty **and** an overlapping slot; the user is told about the penalty (R4) only. This order matters for testing: a test for one rule must use data that breaks only that rule.

#### DT-2 Check-in, no-show and penalty (R7–R9, UC-05 and UC-09)

**Scope.** One `CONFIRMED` reservation of a user on one resource, at the moment `now` (server clock, NFR-10). Two events can happen to it: the owner sends a check-in (E11, C1 = Y), or the System Scheduler runs job J1 without a check-in (C1 = N). Cases handled before this table are a wrong code, no reservation on this resource, a reservation still `PENDING_APPROVAL` and a reservation already `CHECKED_IN` (UC-05 alternative flows 5a, 6a, 6d, 6e).

**Conditions**

| ID | Condition | Rule | Y means |
|---|---|---|---|
| C1 | The owner sends a check-in for this reservation now, with the right QR token or 6-digit code. | R7 | Check-in request (E11). N = scheduler run (J1). |
| C2 | `now ≥ startTime − 10 min` (the check-in window has opened). | R7 | Window has opened |
| C3 | `now ≤ startTime + 15 min` (the check-in window has not closed). Exactly 15:00 minutes after the start counts as Y. | R7, R8 | Window still open |
| C4 | The user has 3 or more `NO_SHOW` reservations whose start is in the last 30 days, this one included (API-A7). | R9 | Penalty threshold reached |
| C5 | The user already has a running penalty. | R9 | Already banned |

**Actions**

| ID | Action | Result |
|---|---|---|
| A1 | Refuse the check-in: too early. | `422 RULE_R7_TOO_EARLY` with `windowOpensAt`. Status unchanged. |
| A2 | Accept the check-in. | `201`, `CheckIn` record (time, method), status `CHECKED_IN` (FR-35). |
| A3 | Refuse the check-in: too late. | `422 RULE_R7_TOO_LATE`. Status unchanged here; A5 follows at the next scheduler run. |
| A4 | No change. | The reservation stays `CONFIRMED`; the window is still open. |
| A5 | Set `NO_SHOW` and free the slot. | Notification `NO_SHOW_RECORDED` (R8, FR-39, FR-40, FR-42). |
| A6 | Create a 7-day penalty (`startsAt = now`, `endsAt = now + 7 days`). | Notification `PENALTY_APPLIED` (R9, FR-41, FR-42). Always together with A5. |

**Impossible combinations.** C2 = N and C3 = N would mean "the window has not opened yet" and "the window has already closed" at the same time. Because `startTime − 10 min` is earlier than `startTime + 15 min`, this cannot happen. The 8 rules with C2 = N and C3 = N (13–16 and 29–32) are marked impossible and removed in step 1.

### 5.6.6 From the decision tables to test cases

Each reduced rule is a test case in the test plan (5.12). The boundary values below are tested in addition, because an error by one minute or one reservation is the most likely implementation mistake.

| Reduced rule | What the test checks | Boundary values |
|---|---|---|
| DT1-1 | Reservation longer than 3 hours is rejected with R1. | 3 h 00 min → accepted (C3 = Y); 3 h 01 min → rejected. |
| DT1-2 | User with a running penalty is rejected with R4. | Penalty ending one minute ago → not running (C1 = N). |
| DT1-3 | Student with 2 active reservations (Academic Staff with 5) is rejected with R2. | Student with 1 active → allowed; a `CANCELLED` or past reservation does not count (D1). |
| DT1-4 | Overlapping request is rejected with R3. | Back-to-back 10:00–11:00 after 09:00–10:00 → free (C2 = Y); a `PENDING_APPROVAL` reservation blocks the slot (D2). Two parallel requests → one succeeds (NFR-08). |
| DT1-5 | Valid `EQUIPMENT` request → `PENDING_APPROVAL`. | — |
| DT1-6 | Valid `ROOM` or `LAB` request → `CONFIRMED`. | — |
| DT2-1 | Check-in inside the window is accepted. | Exactly start − 10 min and exactly start + 15 min → accepted. |
| DT2-2 | Check-in after the window is refused with "too late". | Start + 15 min + 1 s → refused. |
| DT2-3 | Check-in before the window is refused with "too early". | Start − 10 min − 1 s → refused. |
| DT2-4 | Scheduler run inside the window changes nothing. | Run at start + 15 min → still `CONFIRMED`. |
| DT2-5 | First or second no-show → `NO_SHOW`, no penalty. | 2 no-shows in 30 days → no penalty. |
| DT2-6 | No-show of a user who is already banned → `NO_SHOW`, no second penalty. | — |
| DT2-7 | Third no-show in 30 days → `NO_SHOW` and 7-day penalty. | Third no-show with the first one 30 days ago vs 31 days ago (window definition, API-A7). |

### 5.6.7 Assumptions and open points

- **DT-A1.** The rejection reason in DT-1 follows the order of the rule chain in 5.8.4.7 (R1, R4, R2, R3). If the order in the code changes, the full table and the reduced table change with it; the script must then be updated and run again.
- **DT-A2.** DT-2 counts a no-show by the reservation's start time (API-A7).
- **Open.** Whether the no-shows that already caused a penalty are counted again for the next penalty [TBD: H09, Product Owner]. If they are not, C4 changes to "3 or more `NO_SHOW` in the last 30 days that have not caused a penalty yet"; the structure of DT-2 stays the same.
- **Open.** Whether a user with a running penalty may still check in to a reservation made before the penalty started [TBD: 5.4 F3 open point on R4]. DT-2 assumes yes, because R4 only forbids making a reservation.
