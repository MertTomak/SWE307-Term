### 5.3.2 What the literature says, by topic

**Room booking in libraries (sources 1, 2, 8).** All three describe university libraries that moved away from manual booking. Atkinson and Lee show that a free tool can run a room reservation service but moves work to the staff. Perera et al. describe a move from vendor software to a custom interface, and Xuan describes a library-built booking site on a purchased system, improved with student feedback. Xuan adds a practical problem: a purely online system leaves the question of door keys open, and an unused booking wastes a scarce room. This supports two CampusSlot decisions: the rules run automatically (R1–R9), and the interface is designed around what the user has to do at the door.

**QR check-in (sources 3, 4).** Both papers use a QR code to confirm presence, but for class attendance, not for rooms. Masalha and Hirzallah add identity checks with face images and location. Alabi et al. make the code expire after five seconds. CampusSlot takes the idea (scan to confirm) and keeps the data small: a QR code or 6-digit code per resource (FR-31, FR-33), a time window (R7, FR-34) and no biometric or location data (5.10.2).

**Equipment (source 5).** Quickip is the closest source to the `EQUIPMENT` flow: a student requests, and one or more approvers decide. CampusSlot has one approver, the Resource Admin (R5, FR-44 to FR-48).

**Date and time in booking screens (source 6).** The paper compares many ways of showing and entering dates. It gives the team a checklist for the availability calendar. Its results come from airline websites and are not evidence about campus users.

**Space utilisation (source 7).** The utilisation of 19 rooms differed a lot (about 11 % to 88 %). This is the kind of figure the admin occupancy report (F8) is meant to produce.

**What we did not find.** In the eight sources, as far as we read them, we did not find a system that combines rooms, laboratories and equipment under one fixed rule set with a penalty for repeated no-shows. This is a limit of this review (abstracts, a small number of sources), not proof that none exists.

### 5.3.5 What CampusSlot does differently

CampusSlot is a small course project. It is not claimed to be better than the products above. The differences are narrow:

| # | Difference | Requirements | How sure we are |
|---|---|---|---|
| 1 | One fixed rule set for three resource types. A user has an active reservation limit (R2), a time limit (R1) and a ban after repeated no-shows (R9: 3 `NO_SHOW` in 30 days give a 7-day ban). | FR-14 to FR-17, FR-41, FR-43 | The penalty rule is not documented in the product sources read. Some products may let an operator configure something similar. `[TBD: check vendor documentation or a demo]` |
| 2 | Approval only where needed: `ROOM` and `LAB` go straight to `CONFIRMED`, `EQUIPMENT` goes to `PENDING_APPROVAL` with a rejection reason (R5). | FR-18, FR-19, FR-44 to FR-48, FR-55 | 25Live can do much more complex approval. CampusSlot's difference is that the rule is fixed and simple. |
| 3 | Check-in by QR **or** a 6-digit code, with a clear reason when it is refused. | FR-31 to FR-37 | LibCal and Skedda also offer a QR code and a code. This is not a difference in function. |
| 4 | Small personal data: four fields per user, no student number, no face or location (5.10.2). | 5.10.2, 5.8.5 | Stated for CampusSlot only. We did not compare the data of the products. |
| 5 | A stack made of open-source components, built and run by the team (5.10.1, 5.8). | 5.8 | Not a claim about cost. `[TBD: hosting cost scenarios are in 5.11]` |

### 5.3.6 Limits of this review

- Eight core sources is the minimum the task document asks for. Most were read as abstracts.
- Seven of the eight come from library, classroom, laboratory or teaching-room settings. Source 6 comes from airline websites.
- Product information comes from vendor and library pages, which can describe a feature that a given customer has not switched on.
